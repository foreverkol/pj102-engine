# PJ-102-02 · 摄入文件类型支持详解 v1.0

> 基线：v2.0.0-terminal · 依据：ADR-003 L0 文本契约 / ingest_source.py v1.1 实测 / P4-P6 里程碑实战
> 本文回答：本项目能处理什么文件、什么样的文件适合处理、什么样的文件会被拒收或需要预处理

---

## 一、总体契约（L0 文本契约，ADR-003）

**唯一摄入格式：UTF-8 编码的 Markdown 纯文本（.md）**

本项目的 13 步管线（s1-s15）全部围绕"已治理的中文文本"设计，不做音频/视频/图片的直接解析。
录音等原始富媒体须先经外部转文字工具（如千问听悟、WeFlow）转为 .md 后进入本项目。

三条硬性入口校验（不满足即拒收，登记为墓碑可复检）：

| 校验项 | 阈值 | 拒收原因示例 |
|---|---|---|
| 文件大小 | > 0 字节 | 空文件 |
| 中文占比 | ≥ 50% | 英文内容、乱码、编码错误 |
| 发言人标记 | 仅 `transcript` 类强制 | 无"发言人"字样的转写体（chat/note 等类不要求） |

## 二、双层分型体系（v1.1 核心工程）

### 2.1 第一层：命名分型（file_type，按文件名）

| file_type | 命名规律 | 语义 | 示例 |
|---|---|---|---|
| `type1_meeting` | `20YYMMDD[_HHMM]中文…_原文.md` | 录音转写（会议/面谈） | `20230907_083619在苏州酒店与万联网专家详谈_原文.md` |
| `type2_phone_call` | `人名@手机号_20YYMMDDHHMMSS…_原文.md` 或 `20YYMMDD_HHMM人名@描述.md` | 手机通话记录 | `20260829_191607张三通话记录@工具生态选择…md` |
| `unknown` | 不匹配上述两类 | 其他文本（不拒收，照常入管线） | `20260902_2109-张三与千问智能体对话….md` |

**命名约定（与源目录约定一致）**：8 位日期 + 6 位时间为前 15 位唯一标识（录音开始时刻），转化后 .md 文件名前 15 位与原始录音一一对应。日期-标题分隔符支持 `_` 和 `-` 两种变体（T-P4.8 根因修复后）。

### 2.2 第二层：内容分型（file_class，按内容信号）

| file_class | 识别信号 | 典型来源 | 发言人校验 | 实测样例 |
|---|---|---|---|---|
| `transcript` | 首部 2000 字内含"发言人" | 录音转写（千问听悟等） | **强制** | 41 个存量录音源 |
| `chat` | "说话人: 内容"式对话行 ≥ 10 行 | AI 对话导出（千问智能体等）、微信导出 | 不要求 | 0902 千问对话（P4 实战验证） |
| `minutes` | 首部含"会议纪要/议题/决议/参会人员/会议时间/会议地点" | 人工或工具整理的纪要 | 不要求 | L2 压测注入样例 |
| `note` | 非空行中列表项（- * 1.开头）占比 > 50% | 个人笔记、要点清单 | 不要求 | L2 压测注入样例 |
| `article` | 以上皆不匹配（默认兜底） | 文章、报告、长文本 | 不要求 | L2 压测注入样例 |

分型判定顺序：transcript → chat → minutes → note → article（先命中先归类）。

## 三、内容要求（什么样的文本"处理得好"）

### 3.1 处理效果最佳（推荐摄入）

1. **有人物对话/发言结构的转写**——管线 s4 发言人识别、实体抽取、观点归属全链路受益
2. **信息密度高的业务讨论**——涉及具体人名/机构/项目/决策的内容，实体页与判断页产出丰富
3. **单文件 2KB–500KB 的中文文本**——现有 43 个源文件的经验区间；过大文本管线按段落分块处理，无硬上限
4. **连续性主题**——同主题多次会议/通话，cross-meeting 引用与 Synthesis 综合页价值最大

### 3.2 可处理但产出有限

- `article` 类纯文章：无对话结构 → 无发言人归属，判断页 stance 标注可能降级为关键词级
- 单独事件描述（无上下文）：会生成会议页但交叉引用少

### 3.3 会被拒收（勿直接投入）

| 情形 | 处置 |
|---|---|
| 空文件 / 纯英文 / 中文占比 < 50% | 拒收并登记（`status≠ok` 墓碑），修复后自动可复检（T-P4.7） |
| 非 .md 格式（docx/pdf/音频） | 先外部转 .md 再摄入 |
| GBK 等非 UTF-8 编码 | 读入异常拒收，须先转 UTF-8（**注意 BOM：需 UTF-8 无 BOM 或读取端兼容**） |
| 与既有文件内容完全相同 | SHA256 去重跳过（同内容多文件名不重复入池） |

## 四、与 Karpathy LLM Wiki 要求的对照

Karpathy 原始设计：**"把原始素材编译成可导航的知识 wiki"**——素材形态不设限，关键是文本化。
本项目在其基础上收窄为"中文对话/纪要/文章"垂直优化：

| Karpathy 泛化要求 | 本项目落地 |
|---|---|
| 任意文本可入 | 同左（五类分型全覆盖，article 兜底） |
| 来源可追溯 | source 字段 + content_hash + 批次清单全链路 |
| 幂等增量 | SHA256 内容哈希 + status=ok 断点续跑语义 |
| 成本可控 | 批次级成本熔断（--budget-yuan 超限退出码 42） |

## 五、已知边界与扩展方向

1. **9 类富媒体**（图片/语音/视频/文件等微信附件）：当前不支持，属 Phase 2（hermes 主线）范畴
2. **超长单文件**：可处理，但 s2 清洗阶段耗时线性增长；建议单文件 < 1MB
3. **多语言混排**：中文占比 ≥ 50% 门槛内可含英文术语/代码片段（现有语料即如此）
4. **新 file_class**：如需"代码仓库 README""网页剪藏"等类型，扩展点在 `classify_file_class()` 单函数，按 ADR-003 §五 预处理层扩展原则增量添加
